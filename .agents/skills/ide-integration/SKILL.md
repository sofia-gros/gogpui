# IDE連携機能実装フロー (IDE Feature Integration Flow)

gogpuiは、並行して開発される新しいAIDE（Agentic IDE）「goide」の基盤となるレンダリング及びUIフレームワークです。
gogpui側にgoide向けの新しいAPIやUI機能を実装する場合、以下の責務分担と要件を厳守し、実装を行ってください。

## 役割分担の原則

- **gogpui側の責務 (フロントエンド・描画レイヤー)**: 
  GUIのレンダリング、コンポーネント管理、エディタのテキストバッファ描画、イベントハンドリング（キー・マウス）、**シンタックスハイライト（Tree-sitter等の字句解析と色付け）**など、見た目と操作に関わる全てを担います。
- **goide側の責務 (バックエンド・ロジックレイヤー)**: 
  ファイルシステム監視、LSPクライアント通信、Gitコマンド連携、ターミナルPTY管理、AI連携（プロンプト生成とレスポンス処理）などのビジネスロジックを担います。

## goide向けAPI・機能要件

goideから呼び出されるAPIを設計・実装する際は、以下の要件を満たす必要があります。

1. **シンタックスハイライトの完全カプセル化**
   - ファイルのテキストバッファと拡張子（または言語設定）を渡すだけで、gogpui内部でハイライト処理が完結する仕組みとすること。
2. **Virtual Text / Inlay Hint API**
   - LSPからのインレイヒントや、Gitの差分行、AIによるインラインサジェスト（ゴーストテキスト）などを、実際のテキストバッファを汚さずにエディタ上にオーバーレイ描画・挿入描画できるAPIを提供すること。
3. **外部からの装飾・マーカーAPI**
   - goide側がLSPから受け取ったエラーや警告（Diagnostics）の位置情報を渡し、gogpui側で該当箇所に赤波線などを引くためのAPIを提供すること。
4. **リアクティブなUI更新API**
   - LSPのオートコンプリート結果やファイルツリーの更新など、バックエンド（goide）からの非同期なデータ受信に合わせて、メインスレッドをブロックせずにUIコンポーネントを段階的に再描画する仕組みを提供すること。
5. **コマンド・キーバインドレジストリ**
   - goide側から「Ctrl+Pが押されたらファイル検索処理を走らせる」といったイベントフックを登録・上書きできる柔軟なキーバインディング機構を提供すること。

## 手順

1. **要件の確認とAPI設計 (Design the API)**
   - 要求された機能が上記のどの要件に該当するかを確認します。
   - バックエンド（goide）に描画の責務を漏らさず、逆にgogpui側にビジネスロジックを持たせないような、疎結合なAPIシグネチャを設計します。

2. **プランニング (Plan)**
   - APIインターフェース、内部での状態管理（キャッシュ等）、および非同期更新による再描画戦略について Implementation Plan Artifact を作成し、ユーザーに提案・承認を得ます。
   - *注意: gogpui/ggはイミディエイトモードGPU描画であるため、状態管理や再計算のタイミングを正しく設計する必要があります。*

3. **テストの作成と実装 (Implement & Test)**
   - goide側の呼び出しを模した（Mockした）テストやユニットテストを作成し、想定通りにデータを受け取って描画できるか確認します。
   - 実装は責務分担の原則に従い、ロジックレイヤーへの依存を作らないよう注意して行います。

4. **検証 (Verify)**
   - テストスイート（`go test ./...`）が全て成功（Pass）することを確認します。
   - 必要に応じてコンポーネントギャラリー等で描画結果の検証を行います。

5. **報告 (Report)**
   - 変更内容と、APIの利用例、テスト結果を簡潔にまとめてユーザーに報告します。
